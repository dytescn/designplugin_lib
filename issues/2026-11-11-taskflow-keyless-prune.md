# [P1] 任务流输入严格校验：无 `uid` / `name`、键冲突与跨插件覆盖统一返回错误

- 发现日期：2026-11-11
- 代码版本：`plugin_lib` 1.0.20
- 位置：`src/utils/package.rs` `sync_taskflows`（约 858–920 行）
- 状态：讨论中，未执行代码修改；方向为严格校验、非法输入统一返回错误

## 现象

`sync_taskflows` 对没有 `uid` 也没有 `name` 的元素会直接追加：

```rust
None => {
    list.push(item);
    added += 1;
}
```

但 `incoming_keys` 只收集有 key 的元素：

```rust
let incoming_keys: HashSet<String> = incoming.iter().filter_map(taskflow_key).collect();
```

随后在 `prune = true`（`update_plugin` 默认值）时：

```rust
list.retain(|item| {
    let owned = item.get("plugin_uuid").and_then(Value::as_str) == Some(uuid);
    if !owned { return true; }
    taskflow_key(item)
        .map(|key| incoming_keys.contains(&key))
        .unwrap_or(false)   // 无 key => false => 删除
});
```

结果：本轮刚追加的无 key 元素在同一个 `update_plugin` 调用里又被删除；
`install_plugin` 使用 `prune = false`，因此不会删除，两个入口行为不一致。

## 影响

- `taskflow.json` 中忘记写 `uid` / `name` 的元素在安装后“看起来有”，升级后消失；
- `added` / `removed` 计数会同时增加，调用方难以判断；
- 与文档“没有 `uid` 也没有 `name` 的元素会直接追加”的描述不一致；
- 规范要求任务流元素必须有 `uid` 或 `name`，但代码没有拒绝。

## 讨论方案（2026-11-11，未执行）

方向：`taskflow.json` 必须先通过结构校验；不符合规范的内容直接返回错误，不再
“无 key 追加”“静默当空数组”或“更新时再删除”。建议把校验放在任何写入之前
（主表、designdb、kv 都尚未修改时），避免出现部分安装。

### 1. 建议的校验矩阵

| 输入情况 | 建议处理 | 错误码 |
| --- | --- | --- |
| `taskflow.json` 不存在 | 保留原数据，不报错 | — |
| 文件读取失败 | 返回文件错误 | `500300` |
| JSON 解析失败 | 返回参数错误 | `400103` |
| 顶层不是数组，也不是 `{ "taskflows": [...] }` | 返回参数错误 | `400103` |
| `taskflows` 字段存在但不是数组（`null` / 对象 / 字符串） | 返回参数错误 | `400103` |
| 空数组 `[]` | 建议允许，表示显式清空当前插件元素；发布检查再按类型要求 ≥1 | — |
| 元素不是对象 | 返回参数错误，消息带下标 | `400103` |
| 元素是空对象，或既没有 `uid` 也没有 `name` | 返回参数错误，消息带下标 | `400103` |
| `uid` / `name` 存在但不是字符串，或去空白后为空 | 返回参数错误 | `400103` |
| `uid` 和 `name` 同时存在 | 两者都校验；合并键仍优先 `uid` | — |
| 同一包内合并键重复（`uid` 与 `uid`，或 `uid` 与另一个元素的 `name` 相同） | 返回冲突错误 | `400409` |
| `plugin_uuid` 存在但不是字符串 | 返回参数错误 | `400103` |
| `plugin_uuid` 存在且不等于当前插件 UUID | 返回冲突错误，不允许覆盖其他插件 | `400409` |
| 合并键与现有其他插件的元素冲突 | 返回冲突错误，不覆盖现有元素 | `400409` |
| 未知扩展字段 | 允许，保持前向兼容 | — |
| `uid` / `name` 超长或字符集非法 | 待确认后再加限制；见下方问题 | `400103` |

### 2. 需要增加的关键判断

- **空 key 不能当作有效 key**：`uid: ""`、`name: "   "` 目前可能生成空字符串 key，
  必须拒绝。
- **合并键唯一性要跨字段检查**：一个元素的 `uid` 可能与另一个元素的 `name` 相同，
  不能只分别去重。
- **显式 `plugin_uuid` 必须校验归属**：包内写其他插件的 UUID 时拒绝，不能依赖
  `or_insert` 保留外部值。
- **现有元素也要判断归属**：如果 incoming 的 key 命中已有元素，而该元素属于其他插件，
  应返回冲突；当前代码会直接替换。
- **校验发生在 merge/prune 之前**：校验失败时不应追加任何元素，也不应触发 prune。
- **错误消息带位置**：例如 `taskflows[2].uid 必须是非空字符串`，方便定位包内容。
- **区分“没有文件”和“空数组”**：前者保留原任务流，后者显式清空；结构错误不能退化成
  空数组。

### 3. 与现有逻辑的关系

- `read_taskflows` 的 `unwrap_or_default()` 需要改为区分结构错误；
- `sync_taskflows` 在合并前调用统一的 `validate_taskflows`；
- `prune` 只在校验通过后执行；
- 已有历史数据中的无 key 元素如何处理，需要单独约定，不能与“新包非法输入”混在一起。

## 原始建议（仅供对照）

1. 在 `prune` 时保留本轮新增的无 key 元素，例如记录新增元素的索引/标识，
   只清理“更新前存在、且新包中没有”的旧元素。
2. 或者直接拒绝无 `uid` / `name` 的元素，返回 `400103`，与规范一致。
3. 如果决定保留当前行为，至少更新文档和返回值，明确“无 key 元素仅在 install 中保留”。

## 需要确认

- **空数组**：允许作为“清空”语义，还是也按非法输入拒绝？建议允许安装/更新清空，
  由 `chat_plugins` 的发布检查要求至少一个元素。
- **`uid` / `name` 字符集与长度**：是否沿用文档中的 `[a-z0-9_-]+`、长度 ≤ 128？
  这会与已有历史数据兼容性相关，需要先盘点。
- **显式 `plugin_uuid` 不等于当前插件**：返回 `400103` 还是 `400409`？建议 `400409`。
- **历史无 key 元素**：已有 designdb 中的无 key 元素是保留、清理，还是首次校验时报错？
- **兼容开关**：严格校验会让现有不合规包直接失败，是否需要一次性 `strict: false`
  或发布前扫描？
- **校验时机**：是否把 `taskflow.json`（以及 prompts/mcp）的校验统一前置到
  安装/更新写主表之前？这与 `2026-11-11-install-update-retry.md` 的恢复性问题相关。

## 复现思路

1. `taskflow.json` 写入 `[{ "name": "有 key" }, { "desc": "无 key" }]`；
2. 执行 `install_plugin`，确认两个元素都存在；
3. 提升版本后执行 `update_plugin`（默认 `prune = true`），确认无 key 元素消失。
