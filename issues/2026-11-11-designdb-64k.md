## 校验结果（2026-11-11）

| 检查项 | 结果 | 说明 |
| --- | --- | --- |
| designdb 响应上限 | 已修复 | `MAX_RESPONSE_BYTES = 16 * 1024 * 1024`；调用方需分配 `MAX_RESPONSE_BYTES + 1` 字节 |
| designdb 超限行为 | 已更新 | 超过 16 MiB 返回 `-2`，并写入 `code = 500999` 的错误 JSON |
| designdb 测试 | 通过 | `cargo test` 全部通过（含新增的 16 MiB 边界测试） |
| plugin_lib 调用 designdb 的缓冲区 | **未修复，目标 1024 KiB** | `src/utils/designdb.rs` 仍是 `OUT_BUF_SIZE = 65536`；库间目标见 `skills/ffi-buffer.md`。designdb 1.0.3 可写 16 MiB，与 1024 KiB 目标不匹配，需协商或例外 |
| plugin_lib 对外 FFI 缓冲区 | 保持现状 | `src/utils/cjson.rs` 仍是 `OUT_BUF_SIZE = 65_536`；`ts/ffi.ts`、`docs/examples/ffi/call.ts` 也是 64 KiB。对外 FFI 与库间缓冲区分开，不随 1024 KiB 调整 |
| designdb 依赖版本 | 未升级 | `dytes.json` 与 `dytes.lock` 仍是 `designdb 1.0.2` |
| `query_all_at` 固定 20 条 | 未变 | 仍在 `plugin_lib`；16 MiB 提高了单页上限，但不是动态分页 |
| `get_skills` 全量读取 | 部分修复 | 对外只返回摘要，内容改用 `get_skill` 单条读取；内部仍先读取全部匹配文档（含 content）再分页 |
| taskflow 单文档 | 未变 | 仍是全局单文档；16 MiB 只是提高上限，不改变扩展性 |
| `get_functions` / `get_plugins` 的 `page_size` 上限 | 未变 | 仍为 200；大响应会受新的 16 MiB 上限约束 |
| 文档中的缓冲区约定 | 部分更新 | `docs/data-model.md`、`docs/ffi-api.md`、`skills/testenv.md` 已补充库间 1024 KiB 说明；对外 FFI 仍为 64 KiB |

### 结论

- **designdb 侧的问题已修复**：响应上限从 64 KiB 提升到 16 MiB，issue #2 的 designdb 部分可以关闭或标注完成。
- **plugin_lib 侧暂不能直接升级到 designdb 1.0.3**：库间缓冲区目标为 1024 KiB，
  但 designdb 1.0.3 可写 16 MiB，1 MiB 缓冲区仍可能不足。升级前必须与 designdb
  约定响应上限/缓冲区协商，或对 designdb 单独使用 16 MiB + 1 的例外。
- 16 MiB 只是提高上限，**没有解决**固定 20 条分页、`get_skills` 全量读取、
  taskflow 单文档、`page_size` 过大等结构性问题。

### 建议的下一步

1. 按 [skills/ffi-buffer.md](../skills/ffi-buffer.md) 拆分 `database` / `kv_lib` / `designdb`
   的库间缓冲区常量，目标 **1024 KiB**；不要复用对外 FFI 的 `cjson::OUT_BUF_SIZE`。
2. `designdb` 16 MiB 与 1024 KiB 目标冲突需要先确认：由 designdb 限制响应大小、
   增加缓冲区大小协商，或对 designdb 单独使用 16 MiB + 1 的例外；未确认前不要升级依赖。
3. 对外 FFI 的 64 KiB 约定保持不变；`ts/ffi.ts`、`docs/examples/ffi/call.ts`、
   `docs/ffi-api.md` 不随库间缓冲区调整而修改。`database` / `kv_lib` 需各自确认/升级
   自身输出上限后再扩大 plugin_lib 侧缓冲区。
4. 继续评估动态分页、`get_skills` 字段投影、taskflow 存储模型和 `page_size` 上限；
   提高缓冲区不能替代这些结构性改进。
5. 增加大响应集成测试：接近目标上限、超过目标上限，以及 plugin_lib 调用 designdb
   的边界。

## 现象

> 以下为提交 issue 时的原始记录；当前状态以“校验结果”表格为准。

1. `query_all_at` 固定每页 20 条：

   ```rust
   const SCAN_PAGE_SIZE: u64 = 20;
   ```

   `plugin_lib` 的 `designdb::call` 使用 64 KiB 输出缓冲区，响应达到上限时无法完整读取。
   技能 `content` 的 FFI 校验上限是 8000 字符，但安装流程不校验长度；
   即使按 8000 个 ASCII 字符计算，20 条也接近 160 KB；中文 UTF-8 场景更大。
   因此“技能多 / 内容大”时，`sync_skills`、`get_skills` 可能在分页读取阶段失败。

   回复:需要将这个实际问题，整理成issues，发送到desgndb中。(计划是改到16m左右。)

2. `get_skills` 即使 `with_content = false`，也会先 `designdb::query_all(filter)` 读取
   全部匹配文档（含 `content`），再在内存中分页、生成摘要。单页响应超限的风险与
   数据量无关，只与单条文档大小有关。
   
   回复:这个也一样。designdb的接口统一改为16m

3. 任务流整个集合只有一条文档，`taskflows` 是所有插件共享的数组。
   插件数量增长后，`get_taskflow_doc` / `set_taskflow_doc` 的读写请求/响应都可能超过
   64 KiB，导致任务流无法读写。

4. `get_functions` / `get_plugins` 的 `page_size` 上限为 200，单页响应也可能超 64 KiB
   （文档已提示 64 KiB 上限，但没有服务端保护）。

    回复:这个也一样。designdb的接口统一改为16m

## 影响

- 大技能、多插件场景下安装/更新/查询失败，且失败发生在主表写入之后（见
  `2026-11-11-install-update-retry.md`）；
- `get_skills` 的 `with_content=false` 没有减少读取量，性能与内存占用不佳；
- 任务流是全局单文档，扩展性受限，未来可能需要数据迁移；
- 调用方难以区分“响应超限”和“数据为空/库错误”。

## 建议（待商议）

1. 按响应大小动态分页：单条读取或根据 content 长度计算页大小，不要固定 20 条。
2. 如果 designdb 支持字段投影，`get_skills` 摘要查询只取摘要字段，`with_content=true`
   时再按需读取 content；`sync_skills` 只读取 `_id` / `name` / `content` 等必要字段。
3. 任务流考虑按插件/分片存储，或提供分页接口；如果短期不迁移，至少在文档中明确
   容量上限与失败表现。
4. 对 `page_size` 增加服务端大小保护，或返回明确的“响应过大”错误。
5. 为 64 KiB 超限定义稳定错误码/提示，便于调用方重试或缩小范围。

## 需要确认

- designdb 是否支持字段投影、按 id 批量读取或游标分页？
- 任务流存储模型是否允许调整（会影响已有数据与 `update_taskflow` 契约）？
- 是否接受把 `page_size` 上限从 200 降低，或按内容动态调整？

## 复现思路

1. 构造 20 条 content 为 8000 字符的技能，执行 `get_skills` / `install_plugin`，
   观察是否出现 64 KiB 相关错误；
2. 构造大量任务流元素（例如数千条），调用 `get_taskflow`，观察响应是否超限；
3. 用 `with_content=false` 与大 content 技能对比内存/响应，确认仍读取 content。
